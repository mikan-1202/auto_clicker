# 応募・面接用メモ

以下は確認したコードと今回の変更に基づく原稿です。過去の制作部分と今回のAI補助による改善を区別しています。本人の経験や理解を確認せず、開発期間・利用実績・定量的効果は記載していません。

## 履歴書・職務経歴書・ポートフォリオ向け（100〜200文字）

過去にPython・Tkinterで制作したマクロ操作アプリを、現在の知識とAIツールを活用してレビュー・改善しました。既存機能を維持しながら、実行・停止の状態管理、JSON読込時の検証、コード構成を見直しました。回帰テストとREADMEを追加し、第三者が実行・理解しやすい形に整備しました。

## 面接で30秒程度の説明

過去に作った、クリックやキー入力を順番に実行するPythonアプリです。今回、就職活動に向けてAIツールと一緒にコードとGit履歴を確認しました。元々のGUIと実行エンジンの分離を活かし、自然終了後に再実行できない問題や、不正なJSONの読込で現在の一覧が失われる問題を修正しました。テストと実行手順も整備しています。今回の設計提案や実装、テスト作成にはAIの補助を利用しています。

## 「なぜこのように変更したのですか？」への回答例

既存機能を保ちながら、第三者が安心して試せて、処理を追える状態にしたかったためです。例えば再実行の問題は、UIを作り直す必要はなく、停止要求と実際の終了を区別して状態を管理することで対応できました。また、JSONは途中まで読み込んでから失敗する可能性があるので、先に全体を検証してから画面へ反映する形にしました。技術スタックやループの方式は既存のものを残しました。これらの改善にはAIからの提案と実装補助を利用し、回帰テストで挙動を確認しました。

## 技術面接で質問されそうなポイント

| 質問 | このコードに基づく回答の要点 | 説明に必要な知識 |
|---|---|---|
| なぜ別スレッドで実行するのですか？ | GUIのイベントループを待機・入力処理で長時間占有しないため。元々この構造だった | イベントループ、I/O待機、スレッドとGILの違い |
| なぜQueueを使うのですか？ | リスナーからはイベントだけを渡し、GUI更新をTk側の定期処理に集約するため | スレッド間通信、所有権、Tkのスレッド制約 |
| 停止要求と終了はどう違いますか？ | Eventを立てても解放処理中かもしれない。スレッド終了を確認してから再実行を許可する | 協調的キャンセル、競合、join／is_alive、状態遷移 |
| 停止は必ず即時ですか？ | 20ms間隔のGUIポーリングと停止可能な待機を使うが、OSの入力処理やGUIの負荷もあるため即時性は保証しない | スケジューリング、ブロッキング、リアルタイム処理との違い |
| なぜfinallyでreleaseするのですか？ | press後の待機が例外や停止で終わっても、解放を試みる必要があるため | 例外安全性、リソース解放、OS障害時の限界 |
| 入れ子ループはどう動きますか？ | 開始位置と残り回数をスタックに積み、終了行で減算して内側から戻る。既存の方式を維持した | スタック、命令位置、時間計算量と入れ子深さ |
| JSONの型注釈だけでは不十分ですか？ | 型注釈は実行時の値を検査しない。負の時間、NaN、未知キー、ループ不整合を明示的に検証する | 静的型と実行時検証、入力境界、数値の有限性 |
| なぜ実行時にコピーするのですか？ | 一覧やdataclassが後で変更されても実行対象を変えないため。現在のフィールドは単純な値なのでdataclasses.replaceで足りる | 可変オブジェクト、浅いコピー、深いコピー |
| 保存中の障害にはどう対応しますか？ | 同じディレクトリに一時保存してから置換する。置換失敗時に元のファイルを残す | atomic replace、例外処理。電源断に対する完全な耐久性は別問題 |
| テストで本当にクリックしていますか？ | 自動テストではデバイス操作をモック化し、順序・状態・解放を検証する。実機への入力経路の全面保証ではない | モックの範囲、単体テストと結合テスト、実機検証 |
| どこまで自分が作りましたか？ | 過去制作の機能と分離構造は元のGit履歴にある。今回の修正・テスト・文書にはAI補助が大きいと説明する | Git diff、履歴による根拠、AI提案の検証方法 |
| 次に改善するなら？ | 実機入力・複数画面・DPIの確認、GUIからの開始停止、配布検証など。今回実装したとは言わない | 優先順位付け、互換性、適切な検証範囲 |

回答例を暗記するだけでなく、`controller.py`の開始→停止→終了と、`presets.py`の検証→反映の流れを実際に追って説明できることが目安です。
